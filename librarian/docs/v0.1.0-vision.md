# v0.1.0 Vision: HAWP as RAG Context Fetcher & Shaper

**Date:** 2026-07-26, revised 2026-07-27
**Goal:** Ship a minimal, working version incrementally — embeddings + search + reshape,
both ONNX and Ollama, fully verified. Not a fixed feature list against a calendar date.
**Scope:** ONNX + Ollama embeddings, ONNX + Ollama LLM reshaping, search. A RAG/IR
retrieval layer (ranking via a dedicated model) is explicitly **deferred, not core** —
see Tier 2 below.

---

## The Architecture

```
User Query
    ↓
[HAWP Search Layer]
  - Lexical search (fast, recall)
  - Semantic ranking (embeddings, precision)
  ↓
[Retrieval Layer]
  - Document ranking via IR model (MongoDB retriever)
  - Attachment/reference array (which docs were used)
  ↓
[Reshaper Layer]
  - ONNX text2text model OR Ollama LLM
  - Unified Reshaper interface (one abstraction)
  - Restructure + synthesize context
  ↓
[Output]
  - Reshaped markdown
  - Source references (which docs contributed)
  - Pipeline metadata (which backends ran)
```

## Unified Interfaces

### Embedder (Already Shipping in v0.0.3)
```go
type Embedder interface {
    Embed(ctx context.Context, text string) ([]float32, error)
    EmbedBatch(ctx context.Context, texts []string) ([][]float32, error)
    Dimension() int
    Backend() string
    Model() string
    Close() error
}
```

### LLMClient (kept as-is — not renamed to Reshaper)

The interface stays `LLMClient` (`internal/domain/llm/llm_client.go`), not `Reshaper` —
renaming an interface that's already wired through the factory, config, and CLI is churn
without benefit for a generic-vs-simple goal. The `Reshape`/`ReshapeBatch` method names
already read as generic; a new type name wouldn't change what backends can implement it:

```go
type LLMClient interface {
    Reshape(ctx context.Context, content string, maxTokens int) (string, error)
    ReshapeBatch(ctx context.Context, contents []string, maxTokens int) ([]string, error)
    Backend() string
    Model() string
    Close() error
}
```

Implementable by: Ollama LLM (Mistral, Qwen — shipping), ONNX text2text (SmolLM2 —
verified working with a manual `-tags ORT` build, not yet in the release
matrix — see the dedicated section below), future cloud APIs (OpenAI,
Anthropic — see Provider Category below).

### Provider Category: offline vs. online

Every backend (`onnx`, `ollama`, `openai`, `anthropic`) is classified by
`context.BackendCategory(backend)`:

- **`"offline"`** — `onnx`, `ollama`. Runs entirely on this machine once its model is
  present; no per-request API key or internet dependency. **This is the only category
  v0.1.0 ships.**
- **`"online"`** — `openai`, `anthropic`. Calls a third-party API per request; needs a
  key, network access, and incurs per-request cost. Config fields already exist
  (`ContextConfig.Backends.OpenAI/Anthropic`) but are not wired into the embeddings/llm
  factories yet — that's v0.2.0, once there's a real need to pay for it.

This keeps the interface generic (same `Embedder`/`LLMClient` shape works for any future
backend) while keeping v0.1.0's actual surface area small: two offline backends, fully
tested, nothing speculative shipped.

### ContextBlock with Retrieval References (implemented)

```go
type ContextBlock struct {
    Title       string
    Query       string
    ResultCount int
    TokenCount  int
    Budget      int
    Results     []FormattedResult
    References  []DocumentReference  // deduplicated by Source, sorted by Relevance desc
    Metadata    map[string]string
}

type DocumentReference struct {
    Source    string  // file path or URL
    Title     string  // section title
    Content   string  // matched excerpt from this source's highest-relevance chunk
    Relevance float32 // 0.0–1.0 ranking score
    LineStart int     // line range in source, when known (0 = unknown)
    LineEnd   int
}
```

**Rendering: inline, not batched.** Each result's `**Reference:**` line is interleaved
immediately above its own content — not collected into a list at the end — so a reader
(human or LLM) sees which source a chunk came from right where it's used:

```
# Search Results: "kubernetes"

**Reference:** deployment.md (95% relevant)

Kubernetes manages containerized workloads...

**Reference:** architecture.md (82% relevant)

The system uses a declarative API for...
```

The deduplicated `References` array is still available as structured data
(`ContextBlock.References`, or the `references` key in `--format json`) — that's the
shape a downstream retrieval step consumes as reference docs, independent of how the
markdown renders it.

### The "none" backend: zero network, zero model

`embeddings.backend` and `llm.backend` both accept `"none"` (`context.BackendCategory`
returns `"none"` for it — a third category alongside `"offline"`/`"online"`, since it's
not just local, it's *nothing at all*). `NullEmbedder`/`NullLLMClient` implement the
same `Embedder`/`LLMClient` interfaces everything else does — no special-casing needed
by callers, no error path, no fallback warning. `ContextReshaper.Reshape` skips the
embedding/LLM stages entirely when the corresponding backend is `"none"` rather than
routing a no-op prompt through them, so there is genuinely zero network activity:

```bash
HAWP_EMBEDDINGS_BACKEND=none \
  hawp search "kubernetes" --context --max-tokens 400
```

Runs in ~0.6s and produces the same inline-reference-per-chunk structure as the raw
`--context` output — because in null mode, Content *is* that structure
(`formatResultsInline`). Useful when: no Ollama/ONNX available and you still want
structured references; testing the reference-tracking pipeline without waiting on a model;
CI environments with no
model download allowed.

### Work item intake scaffolding: `hawp work new`

```bash
hawp work new "Add search result grouping" --type improvement --input "group results by source document"
```

Generates a UUID, writes an investigation plan file shaped like
`.hawp/kit/templates/work-intake.md`, and inserts a `status: inbox` row into
`BACKLOG.md`'s Active Work table. This is deliberately **only** the mechanical half of
HAWP's intake workflow (`.hawp/kit/usage/intake-workflow.md`) — the Investigation and
Analysis sections are left as `_pending_` placeholders. HAWP is "a shaping protocol, not
a runtime" (`AGENTS.md`); actually investigating a request and writing a plan requires
reasoning about that specific request, which stays a human/AI-agent job. This command
just removes the chore of hand-typing the backlog row and file skeleton every time.

## ONNX Text2Text Model (ORT backend) — Status: WORKING, not yet in the release build

**Verified working end-to-end 2026-07-27** (macOS arm64, manual build): real
ONNX-based text generation via SmolLM2-360M-Instruct, ~1.1s for a
single-context reshape. This was a hard architectural blocker two hours
earlier in the same session — the full path from "blocked" to "verified
working" is worth recording since every step was a real, specific fix, not
a workaround:

1. **hugot only generates via its CGO ORT backend.** The portable Go/XLA
   backend HAWP's embeddings use cannot run generative models at all —
   enforced inside hugot itself (`backends/model.go`:
   `if options.Backend != "ORT" { return error }`). `NewONNXLLMClient` now
   creates the ORT session *before* touching the network — on a default
   `go build` (no `-tags ORT`) this fails instantly with hugot's own
   "to enable ORT, run `go build -tags ORT`" error, so selecting
   `llm.backend: "onnx"` on a normal build never silently downloads an
   ~800MB+ model that can't run.
2. **`-tags ORT` needs three native libraries**, none bundled by default:
   `libonnxruntime`, `libonnxruntime-genai` (a *separate* library
   specifically for generative models — plain ONNX Runtime alone isn't
   enough), and `libtokenizers` (static, from `daulet/tokenizers`). All
   three have official prebuilt releases for 5 of HAWP's 6 target
   platforms — **Intel Mac (macOS x64) has no official Microsoft build of
   either onnxruntime or onnxruntime-genai.**
3. **`WithOnnxLibraryPath` takes a directory, not the library file** — passing
   the file itself fails with "`<path>` is not a directory" (it internally
   joins the directory with the platform-default filename).
4. **Runtime linking needs an embedded rpath**, not just `DYLD_LIBRARY_PATH`:
   `CGO_LDFLAGS` must include `-Wl,-rpath,<dir>` or the built binary fails
   at process start with `Library not loaded: @rpath/libonnxruntime.1.dylib`.
5. **The model itself needs a different HF repo.** The standard
   `HuggingFaceTB/SmolLM2-360M-Instruct` export (used for the original
   benchmark) lacks `genai_config.json` — a Microsoft ONNX Runtime GenAI
   model-builder artifact, not present in the standard optimum/Transformers.js
   ONNX export. Switched to `homen3/SmolLM2-360M-Instruct-ort-genai-int4-cpu`,
   a community genai-format conversion (int4-quantized).
6. **That repo splits weights into a sidecar file** (`model.onnx.data`) —
   `hugot.DownloadOptions.ExternalDataPath` must be set explicitly or the
   session fails at init with "External data path does not exist."
7. **The model needs its own prompt format.** A plain-text prompt made the
   model just echo the input back character-for-character rather than
   following the reshaping instruction — its `chat_template.jinja` expects
   ChatML (`<|im_start|>role\ncontent<|im_end|>`). Wrapping the prompt this
   way fixed it (fully working now for single-context `Reshape()`).
8. **`WithMaxLength` is the total sequence length** (prompt + generation),
   not just new tokens — passing just `maxTokens` fails once the prompt
   alone exceeds it. Now sized from the actual prompt length plus a margin.

**Fixed 2026-07-27 — multi-context `ReshapeBatch()`:** used to fail with
"generation stopped: max length reached" on batches of more than one
context, even under a very generous shared budget. Root cause:
onnxruntime-genai's batch generation doesn't honor per-sequence EOS
independently within a batch, so a longer sequence in the batch forces
every sequence to keep generating past its own stop point — not a
budget-sizing problem, since single-context calls always worked reliably.
Fixed by no longer batching: `ReshapeBatch()` now loops one single-prompt
inference call per context (each gets its own EOS handling, and its own
tightly-sized budget instead of the batch's longest-prompt budget). Costs
N inference calls instead of 1 batched call, but correctness matters more
than that efficiency for a reshaping feature.

**What's needed to ship this** (none of it done yet):
- Wire the GitHub Actions release matrix to build with `-tags ORT` and bundle
  the three native libraries per platform (5 of 6 — Intel Mac needs either a
  from-source build or to ship Ollama-only there).
- General prompt-quality tuning — ChatML fixed the "just echoes input" bug,
  but hasn't been evaluated on a range of real reshaping tasks yet.

**Local dev reproduction** (macOS arm64, what was actually run):
```bash
# Download the three native libraries (once)
mkdir -p ~/.hawp/native/lib ~/.hawp/native/include
# ... fetch onnxruntime-osx-arm64, onnxruntime-genai-osx-arm64,
#     libtokenizers.darwin-arm64 from their GitHub releases, extract
#     .dylib/.a files into ~/.hawp/native/lib/, headers into include/

# Build and test
CGO_ENABLED=1 \
CGO_CFLAGS="-I$HOME/.hawp/native/include" \
CGO_LDFLAGS="-L$HOME/.hawp/native/lib -Wl,-rpath,$HOME/.hawp/native/lib -lonnxruntime -lonnxruntime-genai -ltokenizers -ldl -lm -lstdc++" \
go build -tags ORT ./...
```

## Appendix: HAWP's Role as Context Fetcher

HAWP search is the backbone:
1. **Index:** kit/ + work/ docs with folder context + metadata
2. **Search:** lexical (fast) + semantic (precise)
3. **Rank:** embeddings score relevance
4. **Format:** deduplicate + structure (ContextBlock)
5. **Reshape:** LLM/text2text restructures for clarity
6. **Output:** markdown ready for Claude/user

This v0.1.0 release makes it end-to-end: from raw query to polished, sourced context.
