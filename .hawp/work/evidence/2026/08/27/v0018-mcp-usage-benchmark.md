## Context Efficiency

The savings model for hawp is different from a simple in-vs-out ratio.  
Each `hawp_search` call has a tiny request (a JSON envelope with the query string, ~13 tokens)  
and returns only the relevant chunks from the indexed corpus — not the full corpus.

**Corpus size (indexed):** ~3,138 chunks (re-embedded 2026-08-24 via nomic-embed-text)  
**Average chunks per result set:** varies by query — 0 to ~5 relevant chunks  

| Scenario | Token cost per lookup |
|----------|-----------------------|
| hawp_search (this session avg) | ~934 tokens out per call |
| Read full indexed file (alternative) | typically 2,000–8,000 tokens per file |
| Read entire corpus naively | ~314,000+ tokens (3138 chunks × avg ~100 tok) |

**Selection ratio:** hawp returned chunks from a ~314k-token corpus.  
Each call returned ≤3% of the corpus — targeted retrieval, not full-file reads.

## Observations

1. **Request tokens are nearly free** — the query JSON averages ~13 tokens. The only cost is the response.
2. **Zero-result calls cost ~20–32 tokens** (just the JSON wrapper). No wasted retrieval.
3. **High-recall calls return ~1000–2800 tokens** from a corpus orders of magnitude larger.
4. **Alternative without hawp**: the AI would need to (a) enumerate files, (b) read individual files in full, (c) manage context manually — easily 5–20× more tokens per lookup for the same information.
5. **`hawp_work_validate` did not appear in the log** for this session despite being called. Likely a timing issue: the MCP server exited before flushing the SQLite write. This is a known gap — the validate call's usage is not captured in this evidence set.

## Interpretation

The primary token savings from hawp are **context selection**, not request compression.  
hawp replaces "read the file and figure out what's relevant" with "receive only what's relevant."  
This session shows 9 targeted lookups returning an average of ~934 tokens each from a ~314k-token corpus.  
Equivalent naive file reads for the same queries would have required at minimum 15–45k tokens of file content.

Estimated savings vs. naive file reads: **~10–50× reduction in context read tokens per lookup** (order-of-magnitude, not precisely measurable without a controlled baseline).
