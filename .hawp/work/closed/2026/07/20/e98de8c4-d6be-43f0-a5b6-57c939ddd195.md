# init-time provisioning of db, ONNX Runtime, and models into ~/.hawp

---

### Input (what was reported)

> After `init`, the CLI downloads the ONNX Runtime and models and puts the
> database and models in the `.hawp` folder in the user's home directory.
> Nothing is embedded in the binary.

---

### Context

Follows the 2026-07-20 Go-first decision
(`56067dc8-1cc6-4dbe-8b6d-dd7ffdfea80c`). This realizes the "shared
user-level model/cache folder" preference already recorded in
`54e68af7-4622-4383-8482-cc4d4e1e21ee`: one `~/.hawp/` location that
multiple repos reuse, with the repo-local `.hawp/` staying for kit/work
records only.

---

### Analysis

**Root cause (or most likely cause):**
_Embedding models or the ONNX Runtime in the binary creates large release
artifacts and per-repo duplication; a home-folder cache provisioned on
`init` keeps the binary small and assets shared._

**Directly verified:**
_No database or model download implementation exists yet in `librarian/go/`._

**Inferred (not yet proven):**
_ONNX Runtime shared libraries (per platform/arch) and a small embedding
model (e.g. quantized MiniLM-class, ~25 MB) can be downloaded, checksum-
verified, and loaded from `~/.hawp/` via cgo/ONNX Go bindings._

**Scope — what else is affected:**
_`init` command UX, `~/.hawp/` directory layout (db/, models/, runtime/),
download sources and checksums, offline/failure behavior, platform matrix
(macOS arm64/x64, Linux, Windows), docs in `distribution/`._

---

### Recommended Fix

- Design the `~/.hawp/` layout: database, models, ONNX Runtime library,
  version/manifest file.
- `init` flow: create layout → download ONNX Runtime for the platform →
  download model(s) → verify checksums → record versions in a manifest.
- Make downloads resumable/idempotent; re-running `init` repairs or
  upgrades assets.
- Define offline behavior: lexical features work without models; vector
  features report what is missing.

## Outcome (filled at close)

Closed 2026-07-20. `hawp init` provisions `~/.hawp/{runtime,models,cache/
downloads}` and a `manifest.json` recording installed asset hashes and
versions. Assets are real and verified, not placeholders:

- **ONNX Runtime v1.27.1** — per-platform archives (linux-x64,
  linux-aarch64, osx-arm64, win-x64, win-arm64) from the official GitHub
  release, each pinned by SHA-256 confirmed against the GitHub Releases
  API. Only the shared library is extracted from the archive (skipping
  headers/debug symbols); darwin/amd64 has no upstream prebuilt as of this
  release and fails with a clear "no prebuilt asset" error rather than a
  crash — lexical kit/work commands are unaffected.
- **Xenova/all-MiniLM-L6-v2** (quantized ONNX, 384-dim) — model, tokenizer,
  and config files from HuggingFace, each pinned by SHA-256 (LFS-verified
  for the model, locally hashed for the small text configs).
- Runtime and model provisioning are independent: a runtime failure (e.g.
  unsupported platform) does not block model downloads, and vice versa.
- Downloads verify their SHA-256 while streaming to a temp file before an
  atomic rename; a mismatch never leaves partial or wrong content at the
  destination.
- Re-running `init` checks the manifest + on-disk hash before touching the
  network, making repeated runs idempotent and network-free when nothing
  changed.

Out of scope for this item (per its own framing — "no ONNX/model
integration yet" is the pre-existing status): actually loading the runtime
via cgo/ONNX bindings and running inference. That belongs to `fbf12a93`
(vector search and context building), which can now assume the assets
exist in `~/.hawp/`.
