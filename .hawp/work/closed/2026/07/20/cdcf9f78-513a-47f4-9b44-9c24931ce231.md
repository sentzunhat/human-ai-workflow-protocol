# self-update mechanism for the Go librarian CLI from published releases

**Backlog ID (Legacy):** — (UUID-native item)
**UUID:** `cdcf9f78-513a-47f4-9b44-9c24931ce231`
**Type:** feature
**Reported:** 2026-07-20
**Risk Level:** medium

---

### Input (what was reported)

> The CLI should auto-update from a push of the library — when a new
> release of the librarian is published, installed CLIs pick it up.

---

### Context

Follows the Go-first decision (`56067dc8-1cc6-4dbe-8b6d-dd7ffdfea80c`).
A single static Go binary makes in-place self-update practical (download
new binary, verify, atomic swap) — something the Node/npm path delegated
to package managers.

---

### Analysis

**Root cause (or most likely cause):**
_Without a self-update path, users of a standalone binary drift across
versions and the kit/work format can outrun the tooling._

**Directly verified:**
_No release pipeline or update mechanism exists yet for `golang/`._

**Inferred (not yet proven):**
_A GitHub Releases-based channel (version manifest + platform binaries +
checksums/signatures) is sufficient; an `update` command plus an opt-in
startup check covers the "pushed from the library" behavior._

**Scope — what else is affected:**
_Release CI (cross-compile matrix, tagging), version manifest format,
binary signing/checksums, `~/.hawp/` manifest interplay (model/runtime
upgrades vs. binary upgrades), install docs in `distribution/`._

---

### Recommended Fix

- Decide the release channel (GitHub Releases + checksums first; signing
  later if needed).
- Implement `hawp update`: check manifest → download platform binary →
  verify → atomic replace; clear failure messages, never leave a broken
  binary.
- Decide the auto part: opt-in background check with notice vs. explicit
  `update` only. Default to notify-only, never silent replace.
- Coordinate asset upgrades: binary update may trigger model/runtime
  re-provisioning via `init` (`e98de8c4-d6be-43f0-a5b6-57c939ddd195`).

**What to verify after:**

- [x] Update from version N to N+1 works on macOS and Linux
      (Evidence: `TestApplyDownloadsVerifiesAndReplaces` runs the full
      download-verify-replace path against a local httptest server on
      this machine (macOS arm64); `selfreplace.Replace` is a plain
      chmod+rename with no OS-specific code on non-Windows, so the same
      path applies on Linux. No real release exists yet to test against
      an actual macOS-vs-Linux binary pair — noted as a gap below.)
- [x] Corrupted/partial download never replaces the working binary
      (Evidence: `TestApplyChecksumMismatchLeavesOriginalBinaryIntact` —
      a wrong-checksum release leaves the original exec bytes untouched;
      `download.VerifiedFile` never renames into place on a hash mismatch)
- [x] Update policy (auto vs. notify) documented in distribution docs
      (Evidence: `librarian/go/README.md` "Releasing and self-update"
      section — explicit vs `--check`, no silent/background update exists)

## Outcome (filled at close)

Closed 2026-07-20. `hawp update [--check]` and `hawp version` are
implemented against the real GitHub Releases API (repos/{owner}/{repo}/
releases/latest): version comparison (`internal/domain/update`), a
release client that reads GitHub's auto-computed per-asset SHA-256 digest
(`internal/infrastructure/githubrelease`), and an atomic same-directory
chmod+rename replace (`internal/infrastructure/selfreplace`). Explicit
only — no background/silent auto-update, matching the "default to
notify-only" guidance.

Also lands (from the item's own "what else is affected" scope):
- `librarian/go/Makefile`: `VERSION` variable injected via `-ldflags -X`
  into `internal/domain/update.Version`; defaults to `"dev"` for local
  builds.
- `.github/workflows/release-librarian-go.yml`: inert until a
  `librarian-go-v*` tag is pushed — builds `make dist` and publishes a
  GitHub Release. No tag has been pushed; no release exists yet, which
  `hawp update` reports honestly ("No published releases found yet")
  rather than erroring.
- `.hawp/bin/hawp` wrapper: routes `init`/`version`/`update` to the Go
  binary only (no TS equivalent existed), with a clear error when the
  binary is absent.

**Known gap, tracked for follow-up:** no real release has been published,
so the N→N+1 path is verified against a local httptest fixture, not an
actual two-version release pair. Once the first `librarian-go-v*` tag is
pushed, a manual `hawp update` run against the real release is the
remaining real-world proof.
