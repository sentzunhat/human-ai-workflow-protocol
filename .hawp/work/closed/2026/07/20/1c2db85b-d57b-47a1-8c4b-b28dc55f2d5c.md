product-level decision yet for whether librarian stays a repo-maintenance tree
or becomes a published CLI/binary. The AI-runtime angle adds another layer of
uncertainty because the repo needs a CLI/library runtime, not a browser-centered

**Directly verified:**
_`BACKLOG.md` has no active rows. `README.md` still describes `librarian/` as
repo-local maintenance tooling and `.hawp/bin/hawp` as the repo-local wrapper.
Current primary sources show: Transformers.js supports Node usage and documents
WebGPU/device selection and configurable environment settings including

target._

If the team jumps straight to bundled models or WebGPU, it will likely conflate
three separate risks: command UX, runtime/cache support, and release packaging.
The updated highest-leverage parent lane is transition planning: preserve the
truth of the current Node maintenance tooling while defining the future Go
librarian product around DB/init, ingest, lexical/vector search, and local
context compression for larger-model prompting._

**Scope — what else is affected:**

### Options

#### Option A — CLI-first staged plan

Productize `librarian` as an installable npm CLI first, then run separate spikes
for `transformers.js` Node/WASM runtime viability, shared model cache behavior,
and SEA packaging.

Trade-offs: best separation of concerns; slower to reach "cool demo" binary, but
lowest architectural regret.

#### Option B — AI-runtime-first prototype

Build a proof library/command around `transformers.js` immediately and let the
CLI/binary shape emerge from that prototype.

Trade-offs: faster excitement, but high risk of overfitting the whole CLI to one
runtime/backend path before packaging and command boundaries are stable.

---

### Recommended Fix

**Option chosen:** A
**Rationale:**

The CLI surface, packaging surface, and AI/runtime surface are different
questions. The updated target is a CLI/library path with Node/WASM and shared
filesystem model/cache storage; WebGPU should not be assumed as the foundation.
